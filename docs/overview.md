# Overview

A query passes through four layers:

```text
declarations: handwritten, or generated by relq-codegen
  -> immutable query and expression builders
  -> validation, then a SQLite or PostgreSQL compiler
  -> sqlite3 or asyncpg executor
  -> driver tuples, or rows decoded into a model
```

1. **Schema.** A relation is declared as a `Table`, `DerivedTable`, or
   `CteTable` class. An alias is a typed copy of the same class, so
   `users.as_("manager").id` is still a `Column[int]`. See
   [Schema](./schema.md).
2. **Builders.** `select`, `insert_into`, `update`, and `delete_from` return
   immutable query values. Every method returns a new query. A clause that would
   replace an earlier one, such as `from_`, `values`, `limit`, or `returning`,
   raises `ValueError` if it is set twice. See [Queries](./queries.md) and
   [Data manipulation](./dml.md).
3. **Compiler.** Validation and rendering run over a private AST. A query is
   validated once and rendered for one dialect. Values are bound as parameters.
   The one exception is the constants in a PostgreSQL conflict arbiter
   predicate, which are escaped and written into the SQL (see
   [Data manipulation](./dml.md#conflict-predicates-postgresql-only)). See
   [Dialects](./dialects.md) for what each engine accepts.
4. **Executor.** `relq-sqlite` and `relq-postgres` compile the query inside
   `fetch_*` and `execute`. A fetch returns the driver's own values. A
   `RowAdapter`, or `.decode(Model)` on the query, converts rows into a model.
   See [Execution](./execution.md).

Application code imports query building from the top-level `relq` package, and
migrations from `relq_migrate`. The module layout behind them is in
[Architecture](./architecture.md).
